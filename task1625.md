# JADE-1625: Duplicate orders in workplace Jobpool

## Issue
After updating the workplace Jobpool, order `2000033828` appears twice. Example: CBT shift `04.11.2026`, system/client `T04 / 200`.

## Evidence
Captured at the end of `ZCL_IA_2LOFPM_CLH_WD_ASSIST->GET_JOBPOOL`, before screen binding:

| Debug value | Observed data |
|---|---|
| `IV_PERIM` | `CBT` |
| `IV_MARK` | Blank; the CDS-query branch is skipped |
| `RT_JOBPOOL` | 2 rows for `AUFNR = 002000033828` |
| Row 1 | `ZZPERI = CBT`, `ZSTDKZ = G`, `ZLAGE = RL01`, `ZDIDOK = POZZ` |
| Row 2 | `ZZPERI = GBT`, otherwise matching values in the captured columns |

Duplicates already exist in the method result; they are not introduced by appending rows to the screen.

## Cause / why the perimeter check is insufficient
The building query joins `ZIA_2ORDER AS auftr` with `ZIA_2BUILDING AS gebaeude`.

`WHERE auftr~zzperi = iv_perim` restricts **orders only**. Building matches are checked by building ID/location, without a building-perimeter condition. `SELECT * ... INTO CORRESPONDING FIELDS` includes both tables; shared column names allow building values to overwrite order values. The observed result contains the same order under both `CBT` and `GBT`.

## Implemented workaround
File: `ZCL_IA_2LOFPM_CLH_WD_ASSIST\ZCL_IA_2LOFPM_CLH_WD_ASSIST.abap`  
Method: `GET_JOBPOOL`

Immediately before `ENDMETHOD`, after both query branches:

```abap
IF iv_perim IS NOT INITIAL.
  DELETE rt_jobpool WHERE zzperi <> iv_perim.
ENDIF.
```

For the captured CBT case, this removes the GBT row and retains the CBT row. No `IV_MARK` check is required. The non-initial guard matters because the non-building caller does not supply `IV_PERIM`.

The original queries remain unchanged; the earlier proposed `EXISTS` rewrite was removed in favor of this minimal filter.

## Verification / limitations
**SAP verification pending:** activate the method, repeat the workplace update, and confirm one row for `002000033828` with `ZZPERI = CBT`. Check GBT, repeated updates, newly created eligible orders, and the caller with blank `IV_PERIM`.

This is a perimeter-filter workaround, not general deduplication: same-perimeter duplicates remain, and the joined `SELECT *` can still overwrite other shared fields. A query-level correction is needed if those cases occur.
