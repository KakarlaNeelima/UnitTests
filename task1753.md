# JADE-1753: Resetting or deleting a shift leaves planning orders with PL1/PL2

## Issue

When a shift is reset or its work area is deleted, planning orders can remain with user status `PL1` or `PL2` instead of `REAL`.

## Description

When a shift is reset, some planning orders still have user status `PL1` or `PL2`.

Example:

The shift must be Dispo released before testing.

## Test requirements

### Reset shift on the starting page

Use GBT shift `1500004173` in T04:

- Date: `12.10.2026`
- Shift: `1500004173`

### Reset shift on the detail page

Use GBT shift `1500004174` in T04:

- Date: `12.10.2026`
- Shift: `1500004174`

### Delete work area

Use GBT shifts `1500004175` and `1500004176` in T04:

- Date: `12.10.2026`
- Shift `1500004175`
- Shift `1500004176`

## Expected result

After resetting the shift or deleting the work area:

- All affected planning orders must have user status `REAL`.
- User statuses `PL1` and `PL2` must not be active.

## Steps to overcome

### 1. Correct the status handling

Update the reset and work-area deletion logic so **every planning order** linked to the affected work area is processed. Do not use only `lo_orders->map[ 1 ]`.

In `ZCL_IA_2WORKSHIFT->RESET`, iterate through all orders in `lo_orders` and deactivate `PL1`, `PL2`, and `PL3` for each order before removing the order from the work area:

```abap
DATA(lo_order_iterator) = lo_orders->get_values_iterator( ).

WHILE lo_order_iterator->has_next( ) = abap_true.
  DATA(lo_order) = CAST zcl_ia_2order( lo_order_iterator->get_next( ) ).

  lv_order = lo_order->get_id( ).

  me->deactivate_user_status(
    iv_qmnum = CONV zia_2_workshift( gs_schicht-zschicht )
    iv_order = lv_order ).
ENDWHILE.
```

For work-area deletion, apply the same processing in `ZCL_IA_2WORKSHIFT->REMOVE_ARBEITSSTELLE` before `io_object->remove_auftraege( iv_change_erp = abap_false )`. Deactivation must be performed for every order returned by `io_object->get_auftraege( )`.

Keep the existing ERP restore, order removal, vehicle removal, work-area cleanup, and database deletion logic unchanged. The change is limited to explicit user-status cleanup.

### 2. Centralize the logic

Prefer reusing `ZCL_IA_2WORKSHIFT->DEACTIVATE_USER_STATUS` for reset and work-area deletion.

For each order:

1. Verify that the shift number and order number are not initial.
2. Read the order object number.
3. Read the active user statuses.
4. Deactivate `PL1`, `PL2`, and `PL3` when active.
5. Commit or handle the SAP status-change result consistently.

Do not deactivate statuses for orders that are no longer assigned to the affected work area.

### 3. SAP test procedure

Before testing, use disposable test shifts and ensure each shift is Dispo released.

1. Open the GBT starting page.
2. Reset shift `1500004173` in T04.
3. Verify that all planning orders assigned to that shift have user status `REAL` and no active `PL1` or `PL2`.
4. Open GBT shift `1500004174` and reset it from the detail page.
5. Verify the same status result.
6. Open GBT shift `1500004175`, delete its work area, and verify all linked planning orders.
7. Repeat for GBT shift `1500004176`.

Check all linked planning orders, not only the first order in the work area.

### 4. Regression checks

- Reset with one planning order.
- Reset with multiple planning orders in the same work area.
- Reset with an empty work-area order map.
- Reset from the starting page.
- Reset from the shift detail page.
- Delete a work area with multiple planning orders.
- Delete an empty work area.
- Verify that existing `REAL` status remains correct and `PL1`/`PL2` are not left active.
